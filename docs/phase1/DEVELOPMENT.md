## 0. 이 문서의 위치와 출처

바이브 코딩(AI와 함께 코드를 쓰는 방식)으로 개발하므로, **코드가 빨리 써지는 만큼 "왜 그렇게 썼는지"를 기억하는 사람이 없어지는 위험**을 규칙으로 막는 문서다. 수정 요청이나 오류 개선은 **추측이 아니라 로그와 실제 브라우저 화면으로 확인한 사실**을 근거로 한다.

**참고한 자료**: 규강의 다른 프로젝트 NexusPM의 개발 문서(`docs/engineering/DESIGN.md` 구현 설계 원칙, `DEVELOPMENT.md` 개발·검증 지침, `DEPLOY.md`, `AGENTS.md`, 정밀 감사 기록). 문장을 옮기지 않고 원칙을 이 프로젝트에 맞게 다시 썼다.

**NexusPM과 다른 점 — 그대로 가져오지 않은 것**

| NexusPM | 이 프로젝트 | 영향 |
| --- | --- | --- |
| 개인용 로컬 앱, 사용자 1명, `127.0.0.1`에만 바인딩 | **인터넷에 공개되는 사이트** + 관리자 화면 | 보안 요구가 훨씬 크다 ([SECURITY.md](SECURITY.md)) |
| 파일이 원본, DB는 보조 인덱스 | 콘텐츠는 DB가 원본일 가능성이 크다 (스택 미정) | 계층 분리 원칙은 유지, 파일 입출력 규칙은 제외 |
| 로그인 시도 제한이 앱 전체 1개 버킷 | 여러 방문자가 접속 | 시도 제한을 IP·계정 기준으로 다시 설계 |
| Next.js 16, SQLite, npm 고정 | **프레임워크는 Next.js 16으로 확정(§12), 호스팅·DB는 열린 결정** | 지침은 스택 중립으로 쓰고, 확정된 항목만 §12에 채운다 |

**상태 표기**: 이 문서는 지침이다. 구현 상태는 항목별로 [CHANGELOG](CHANGELOG.md)와 [ADMIN-DESIGN](ADMIN-DESIGN.md)의 구현 기록에 있다. 구현되지 않은 것을 구현됐다고 쓰지 않는다.

## 2. 고정 작업 순서 — 추측으로 고치지 않는다

수정 요청, 오류 개선, 신규 기능 모두 같은 순서를 따른다: **관측 → 가설 → 원인 경계 특정 → 작은 변경 → 검증 → 발행.**

### 2.1 변경 종류별 시작점

| 종류 | 작업 전에 확보할 것 | 완료 근거 |
| --- | --- | --- |
| 오류 수정 | 재현 입력·순서, 기대와 실제의 차이, **수정 전 화면·로그** | 같은 재현이 통과하고 회귀 테스트가 남음 |
| 화면 수정 요청 | **현재 화면 캡처**, 관련 명세([SCREEN-SPEC.md](SCREEN-SPEC.md))와 디자인 시스템 | 수정 전후 같은 조건의 캡처 비교 |
| 개선·리팩터링 | 기존 동작·성능 기준과 보존할 계약 | 전후 비교, 기존 동작 유지 |
| 신규 기능 | PRD 조항, 수용 시나리오(빈 상태 포함), 화면·입출력 계약 | 정상·오류·취소·재시도 시나리오 검증 |
| 문서·설정 | 참조 경로, 영향 범위 | 링크·실행 명령 검사. 설정은 빌드까지 |

### 2.2 7단계

1. **범위 정의** — 근거 명세, 사용자에게 보일 변화, 바꾸지 않을 조건, 영향 파일, 위험과 되돌리는 방법을 적는다.
2. **재현** — 커밋, 런타임, 브라우저, **화면 크기(390 / 768 / 1440)**, 데이터를 기록한다. 실제 신청자·후기 같은 개인정보가 아니라 **가상 데이터**를 쓴다.
3. **증거 확보** — 필요한 것만 모은다: 실패 화면, 요소의 계산된 스타일, 요청·응답·시간, 같은 조작의 서버 로그, 저장 전후 DB 상태.
4. **경계 좁히기** — 사용자 조작 → 화면 상태 → 서버 요청 → 입력 검증 → 업무 규칙 → 저장 → 응답 → 재표시 순서에서 **처음 기대와 다른 지점**을 찾는다. 관측한 사실과 가설을 따로 적는다.
5. **최소 변경** — 원인이 있는 계층을 고친다. 통신 실패를 CSS로 가리거나, 겹침을 큰 `z-index`로 덮지 않는다.
6. **검증** — 회귀 테스트, 공통 게이트(§7), 영향 흐름의 실제 브라우저 시험. 화면은 수정 전후 같은 크기·데이터·상태로 캡처하고 **실제로 열어 읽는다.**
7. **발행** — diff와 보존 조건 확인 → 논리 단위 커밋 → 요청 범위 안에서 푸시. 실패와 미검증을 숨기지 않는다.

재현이 안 되면 "재현 불가"로 기록하고 입력·환경 차이를 조사한다. 원인 없이 "수정 완료"라고 하지 않는다. 긴급 완화는 가능하지만 원인 해결과 구분하고 후속 과제를 남긴다.

## 3. 구조와 계층

```text
app/
├── (public)/      # 공개 사이트 라우트 — 얇게. 데이터 조회와 화면 조립만
├── admin/         # 어드민 라우트 — 모든 요청에서 인증·권한을 서버에서 다시 검사
├── api/           # 외부에서 호출되는 엔드포인트 (폼 제출, 웹훅 등) — 최소화
components/
├── ui/            # 디자인 시스템 기본 요소 (Button, Badge, Card ...)
├── site/          # 공개 사이트 조합 (SiteHeader, StoryCard, TourCard ...)
└── admin/         # 어드민 조합
lib/               # 비즈니스 로직 — 순수 함수. 화면도 DB도 모른다
data/              # DB·스토리지·메일 등 외부 접근의 유일한 관문
config/            # 상수·설정 (단일 출처)
types/             # 콘텐츠 스키마 (입력 검증과 타입을 하나에서 파생)
tests/             # 단위·E2E
```

세부 폴더는 스택 확정 시 조정할 수 있지만 **계층 규칙은 고정**한다.

- 의존 방향: `app(서버) → data → lib(순수 로직)`. 클라이언트 컴포넌트는 서버로 저장을 요청하고 브라우저에서 안전한 순수 함수만 재사용한다.
- **화면은 DB·스토리지를 직접 만지지 않는다.** 모든 읽기·쓰기는 `data/`를 거친다. 공개/비공개 필터링이 한 곳에서 보장되려면 관문이 하나여야 한다 ([SECURITY.md](SECURITY.md) §4).
- 서버 전용 모듈(DB, 시크릿 사용)이 클라이언트 번들에 들어가는 것을 금지한다.
- 콘텐츠 스키마는 `types/`에 하나만 둔다. 입력 검증, 타입, 어드민 폼이 모두 이를 참조한다. 명세가 바뀌면 스키마가 먼저 바뀌고 코드가 따라온다.
- 코드(변수·함수·파일명)는 영어, 사용자에게 보이는 문구는 한국어. 주석은 **"왜"만** 쓴다. "무엇"은 코드가 말한다.
- 매직 넘버·매직 문자열 금지. 상수는 `config/`로. 고정 문구는 코드에 박지 않고 사이트 설정에서 관리한다 (PRD W-7).
- 사이트 주소는 `SITE_URL` 환경변수 한 곳에서만 정의한다 (PRD §5 도메인 독립성).
- 디자인은 [DESIGN-SYSTEM.md](DESIGN-SYSTEM.md)의 토큰과 컴포넌트를 쓴다. 색상·글꼴·간격을 코드에 직접 쓰지 않는다.

## 4. 분야별 진단 기준

### 4.1 프런트엔드 — 보이는 화면의 실제 상태

- 수정 전에 **실제 앱 화면을 캡처**한다. 코드를 읽는 것만으로 화면을 봤다고 하지 않는다.
- **레이아웃·글자 잘림**: 대상 요소와 부모의 크기, `display`, flex/grid, `overflow`, `min-width`, `white-space`를 확인한다. 가로 넘침은 `scrollWidth > clientWidth`로 찾는다. 이미 알려진 사례: 모바일 시안의 글자 잘림 (원인 후보는 [DESIGN-SYSTEM §7](DESIGN-SYSTEM.md)).
- **레이어·클릭 문제**: 덮는 요소, `pointer-events`, 쌓임 맥락, 포털 위치를 함께 본다. 큰 `z-index`로 덮지 않는다.
- **상태 문제**: 입력 → 이벤트 → 상태 → 재렌더링을 추적한다. 서버 저장이 성공해도 화면이 안 바뀌면 실패다. 새로고침으로 문제를 감추지 않는다.
- 항상 확인하는 상태: 정상 / 로딩 / **빈 상태** / 검증 오류 / 저장 실패 / 비활성 / 키보드 포커스 / 좁은 화면.

### 4.2 서버·API — 계약과 조작 단위 추적

- **HTTP 성공 코드만으로 업무 성공을 판단하지 않는다.** 반환값과 실제 저장 결과를 확인한다.
- 입력 스키마, 권한 경계, 업무 규칙, 응답 계약을 먼저 정한다. 잘못된 입력, 존재하지 않는 대상, 중복 제출, 외부 서비스 실패(메일, 스토리지)를 시험한다.
- 핵심 조작은 구조화 로그를 남긴다 (§5).
- 정상 경로와 실패 경로를 같은 입력으로 다시 시험하고, 반환값·부작용·사용자 안내가 같은 사실을 말하는지 확인한다.

### 4.3 데이터 — 저장 결과와 복구 가능성

- 성공 응답만으로 저장 성공을 보고하지 않는다. 쓰기 전후의 행 수와 값을 비교한다.
- 시험은 **운영과 분리된 DB**에서 한다. 운영 데이터를 시험 명령으로 지우지 않는다.
- 스키마 변경(마이그레이션)은 적용·실패·되돌림 계획을 함께 쓴다. 삭제·덮어쓰기가 가능한 변경은 백업과 복원 경로부터 확보한다.
- 공개 여부(`draft`, 비공개 후기·장비)는 **저장 시점이 아니라 조회 시점에도** 걸러지는지 시험한다.

### 4.4 인프라·접속 경로

- 시작 명령 → 프로세스·포트 → 요청 도달 → 앱 로그 → 응답을 순서대로 확인한다. 빌드 성공과 실행 성공, 실행 성공과 사용자 접속 성공을 구분한다.
- 환경변수·권한·런타임·도메인·HTTPS 변경은 영향 경계별로 점검한다. **시크릿 값 자체는 출력하지 않는다.**
- 프리뷰·스테이징은 가상 데이터와 분리된 DB만 쓰고 실제 신청자 정보를 넣지 않는다.
- 호스팅이 정해지면 §12에 접속 경로와 로그 확인 방법을 적는다.

## 5. 로깅

**로거 모듈 하나**를 만들어 모두가 쓴다. 호스팅의 로그 수집 방식이 정해지면 출력 형식을 맞춘다.

| 수준 | 의미 |
| --- | --- |
| `error` | 기능 상실 |
| `warn` | 기능 저하, 계속 동작 (메일 발송 재시도 등) |
| `info` | 핵심 조작의 기록 |
| `debug` | 진단용. 운영에서는 끈다 |

**구조화 필드** (채택 기준이며, 구현 전에는 대기 상태다)

| 필드 | 설명 |
| --- | --- |
| `operation` | 조작 이름 (예: `inquiry.submit`, `story.publish`) |
| `operationId` | 요청부터 응답까지 이어지는 식별자. 경계를 넘어 전달해 요청·저장·응답을 연결 |
| `target` | 대상의 **비민감 식별자** (글 ID, 투어 ID) |
| `outcome` | `success` / `rejected` / `failed` |
| `durationMs` | 소요 시간 |
| `errorKind` | 오류 종류 (검증, 권한, 외부 서비스, 알 수 없음) |

**반드시 로그를 남기는 조작**: 투어 신청·문의 접수와 처리, 글·투어·장비·후기의 발행·수정·삭제, 어드민 로그인 성공·실패·로그아웃, 파일 업로드(허용·거부), 알림 메일 발송 결과, 권한 거부, 스팸 차단.

**로그에 남기지 않는 것**: 이름·연락처·이메일·문의 본문 같은 **개인정보**, 비밀번호, 세션·인증 토큰, 쿠키, 전체 환경변수, 요청 본문 전체. 필요하면 마스킹하거나 식별자로 대체한다. (캡처와 Playwright 추적 파일에도 같은 기준을 적용한다.)

- 흩어진 `console.log` 금지. 진단 출력도 로거로 쓴다.
- 로그 파일은 저장소에 커밋하지 않는다.
- 로그와 화면이 같은 사실을 말해야 한다. 예: 화면에 "접수되었습니다"를 보이는데 로그에 `failed`가 있으면 결함이다.

## 6. 오류 처리

- 빈 `catch` 금지.
- 사용자에게 보이는 오류 메시지는 **친절한 한국어**, 상세(스택·경로)는 로그에만. 문구 톤은 [CONCEPT §7.2](CONCEPT.md)의 시스템 안내 문체를 따른다.
- 외부 조작(메일, 스토리지, 외부 API)은 실패 경로를 항상 정의한다. 예: 메일 발송이 실패해도 **신청 데이터는 저장하고**, 실패는 로그와 어드민에 표시한다 (신청을 잃지 않는다).
- 폼 제출 실패 시 **입력한 내용을 보존**하고 다시 시도할 수 있게 한다.

## 7. 검증 게이트

| 변경 범위 | 필수 검증 |
| --- | --- |
| 문서만 | 상대 링크, 분류, 상호 참조, 버전 표, diff |
| 코드·설정·의존성 | 타입 검사 + 린트 + 단위 테스트 + 빌드 (명령은 스택 확정 후 §12) |
| 화면·동작 | 위 게이트 + **영향 흐름의 실제 브라우저 시험 + 수정 전후 캡처를 열어 읽기** |
| 저장·마이그레이션 | 분리된 DB의 전후 비교, 실패 경로, 되돌림 가능성 |
| 인증·권한·업로드 | 위 게이트 + [SECURITY.md](SECURITY.md) §15 시나리오 |
| 실행·배포 | 프로세스·응답·환경변수 분리·데이터 분리 확인 |

**버그 수정 = 회귀 테스트 추가.** 수정 전 실패하고 수정 후 성공하는 테스트를 남긴다. 실패 기준을 쓰지 않은 신규 기능은 구현에 착수하지 않는다.

**판정 용어**: 통과(실제 실행 증거가 있음), 실패(기대와 다름), 미검증(실행하지 않음 또는 환경 불가), 대기(선행 기능 미구현). 실행하지 않은 검증을 통과라고 쓰지 않는다. 사용자가 "의견 없음"이라고 한 것을 전체 통과로 확대하지 않는다.

## 8. 브라우저 검증 — 로그와 화면을 함께

**도구**: Playwright를 기본으로 한다 (역할·이름 기반 요소 탐색, 자동 대기 단언, 추적 파일). AI 세션의 내장 브라우저로 직접 열어 보는 것은 **보조**이며 자동화 테스트를 대체하지 않는다.

| 증거 | 목적 | 주의 |
| --- | --- | --- |
| 수정 전후 전체 화면·문제 영역 캡처 | 위치·겹침·가독성 비교 | **이미지를 열어 읽고** 구체적으로 기록. 캡처 저장 성공을 기능 성공으로 대체하지 않는다 |
| 사용자 흐름 단언 | 생성·이동·저장·취소 | 새로고침 전 화면 갱신과 영속 저장을 따로 확인 |
| 계산된 스타일·DOM | 크기·상태·쌓임 원인 | 화면에서 본 문제와 연결 |
| 브라우저 콘솔 오류·실패 요청 | 실행·통신 문제 | 예상된 검증 오류와 예기치 않은 오류 구분 |
| 서버 로그 | 화면 뒤의 실제 부작용 | 같은 `operationId`로 화면 조작과 연결 |
| 추적 파일 | 조작 순서·DOM·네트워크 상관 | 실패 시 보존. 항상 녹화하지 않는다 |

**화면 크기 세트**: 390(모바일), 768(태블릿), 1440(데스크톱). 모바일 가로 넘침과 글자 잘림은 매번 확인한다.

**시험 환경 규칙**: 시험용 서버와 DB는 운영·개발 환경과 분리하고 시험마다 가상 데이터를 만든다. 기존 서버·사용자 데이터를 재사용하지 않는다. 고정 시간 대기와 취약한 DOM 순번 선택을 피한다. 시각 회귀 기준 이미지는 글꼴·브라우저·데이터·시간을 고정하고 검토 후 승인한다. **자동 차이율만으로 좋은 화면이라고 하지 않는다.**

증거에는 입력·응답·링크가 담길 수 있으므로 가상 데이터를 쓰고, 공유 전에 검토한다. 원시 증거(캡처, 추적, 리포트)는 git 무시 경로에 두고 정제한 결과만 문서에 기록한다.

## 9. git과 문서 버전

- **커밋 하나 = 논리적 변경 하나.** 접두어: `feat` `fix` `docs` `chore` `refactor` `test` + 한국어 또는 영어 요약. 본문에 근거 명세(PRD 조항)를 적는다.
- **main에 직접 푸시하지 않는다.** 기능 브랜치 → PR → 규강 검토 후 병합 ([PRD §11](PRD.md)). 경로를 분리해 충돌을 줄인다 (`app/`, `docs/phase1/`).
- 실험은 임시 브랜치에서 하고 검증 후 가져온다.
- **태그**: 마일스톤마다 주석 태그로 되돌아갈 지점을 만든다 (SemVer, 0.x는 초기 개발). 후보와 확정을 구분하고 태그 본문에 범위와 미검증 항목을 적는다.
- **문서 버전**: [CHANGELOG.md](CHANGELOG.md)의 규칙을 따른다. 코드 변경이 명세를 바꾸면 문서를 같은 PR에서 고친다. **코드가 혼자 옳아지는 침묵의 어긋남을 금지한다.**
- 시크릿이 커밋에 들어갔다면 **키 교체가 첫 조치**이고 이력 정리는 그다음이다.
- 커밋·푸시는 사용자가 요청한 경우에만 한다.

## 10. 기술 선택과 버전 원칙

| 대상 | 규칙 | 금지 |
| --- | --- | --- |
| 런타임 | LTS만. EOL 전에 지원 기간 안에서 이전 | 홀수 버전, EOL이 지난 버전 |
| 프레임워크 | 현행 안정 메이저. 새 메이저는 출시 후 약 한 달, 패치가 안정된 뒤 | canary·beta·RC, 출시 당일 채택 |
| 라이브러리 | ① 최근 12개월 내 유지보수 ② 널리 쓰임 ③ **상업 이용 가능한 무료 OSS 라이선스** (마켓 확장 고려) | 유지보수가 끊긴 것, 중복 기능 라이브러리 |
| 버전 고정 | lockfile. 업데이트는 `chore:` 커밋으로 **한 번에 하나** | 여러 개를 한 커밋에 |
| EOL 점검 | 채택 전 + 분기별로 확인 | 확인 없이 도입 |

**긴급(보안) 예외 경로**: 같은 메이저 안의 보안 패치는 지체 없이 적용한다. 보안 때문에 새 마이너·메이저가 필요하면 한 달 유예 없이 올리되 **안정 릴리스만** 대상이다. 공식 보안 공지로 근거를 확인하고, 기술 결정 로그에 날짜·사유·되돌리는 방법을 적고, **검증 게이트는 생략하지 않는다.**

**교체 가능한 경계**: 메일 발송, 이미지 스토리지, 분석, 캡차처럼 외부 서비스에 기대는 부분은 `data/`의 어댑터 뒤에 둔다. 호스팅이나 서비스를 바꿔도 나머지 코드가 흔들리지 않게 한다. (호스팅이 열린 결정이므로 중요하다.)

새 패키지는 설치 전에 라이선스, 유지보수 상태, 설치 스크립트 유무를 확인한다 ([SECURITY.md](SECURITY.md) §11). 스펀지클럽 스타터 키트 같은 **학습용 자료의 파일은 저장소에 복사하지 않는다** ([PRD §10](PRD.md)).

## 11. AI 협업 원칙 — 바이브 코딩 운영 규칙

1. **규약은 저장소에 산다.** 루트에 `AGENTS.md`를 두고 읽는 순서(PRD → 이 문서 → SECURITY → 해당 화면 명세 → 디자인 시스템), 고정 스택, 금지 사항, 검증 명령을 적는다. 코드 착수 시 가장 먼저 만든다. (아직 없음. 대기)
2. **변경 루프는 §2의 7단계다.** 요청 하나 = 과제 하나.
3. **범위 규율.** AI가 "겸사겸사 고쳤다"고 제안하면 기록하고 별도 요청으로 처리한다. 변경 단위를 알아볼 수 있어야 커밋 설명과 되돌리기가 쉽다.
4. **명세 우선.** 구현과 명세가 어긋나면 코드를 고치거나 명세를 개정한다.
5. **컨텍스트를 준다.** 변경을 맡길 때 관련 파일과 해당 명세 조항(PRD ID, 화면 설계서 요소 ID)을 함께 준다.
6. **확인이 필요한 결정은 질문 도구로 묻는다.** 사용자의 결정이 필요한 것(범위, 선택지, 커밋·푸시, 비가역 작업)은 선택지를 제시하고 답을 받은 뒤 진행한다. 기본값이 분명한 사소한 선택은 기본값으로 진행하고 알린다.
7. **비가역 작업은 먼저 확인한다.** 삭제, 강제 푸시, 운영 데이터 변경, 외부 서비스 발송.
8. **보고는 정직하게.** 통과·실패·미검증·대기를 구분하고, 실행하지 않은 검증을 숨기지 않는다.

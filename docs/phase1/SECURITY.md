> 이 문서는 설계 지침이며 **법률 자문이 아니다.** 개인정보와 전자상거래 관련 의무는 공개 전에 전문가 확인을 권한다. 코드가 아직 없으므로 모든 통제의 구현 상태는 "대기"다.

## 0. 위치와 위협 모델

NexusPM의 보안 설계(로컬 전용 바인딩, 관리자 로그인, 시크릿 분리, "인증 없는 노출 금지" 원칙, 감사에서 드러난 결함 유형)를 참고하되, NexusPM은 **개인 PC에서 도는 앱**이고 이 사이트는 **인터넷에 공개**된다. 그래서 같은 원칙도 통제 수준이 다르다.

### 0.1 지켜야 할 자산

| 자산 | 위험 |
| --- | --- |
| 투어 신청자의 개인정보 (이름, 연락처, 이메일, 문의 내용) | 유출, 무단 열람, 스팸 악용 |
| 관리자 계정 | 탈취되면 사이트 변조, 데이터 유출 |
| 공개 전 콘텐츠 (임시저장 글, 비공개 후기·장비) | 의도치 않은 공개 |
| 후기 작성자 정보와 원문 | 동의 없는 공개 |
| 사이트 콘텐츠와 브랜드 | 변조, 악성 스크립트 삽입 |
| 시크릿 (DB 접속 정보, 메일·스토리지 키) | 유출 시 전체 시스템 위험 |
| 향후 마켓의 주문·결제 관련 정보 | 금전 피해, 법적 책임 (§17) |

| 위협 | 예 |

| 입력 악용 | 리치 텍스트·댓글류 입력을 통한 XSS, SQL 삽입, 메일 헤더 삽입 |
| 접근 통제 우회 | 비로그인으로 어드민 접근, 임시저장 글 URL 추측, 신청 목록 조회 |

| 개발 과정의 유출 | 로그·캡처·추적 파일에 담긴 개인정보 |

## 1. 원칙

| # | 원칙 | 뜻 |
| --- | --- | --- |
| 1 | 기본 거부 | 명시적으로 허용한 것만 열린다. 어드민과 비공개 데이터는 기본이 닫힘 |
| 2 | 서버가 판단한다 | 화면에서 버튼을 숨기는 것은 보안이 아니다. 인증·권한·검증은 서버에서 매번 한다 |
| 3 | 최소 수집, 최소 권한 | 필요한 개인정보만, 필요한 권한만 |
| 4 | 검증된 방식만 | 암호·인증·세션을 직접 발명하지 않는다. 표준 알고리즘과 검증된 라이브러리를 쓴다 |
| 5 | 안전한 기본값 | 설정을 빠뜨려도 안전한 쪽으로 동작 |
| 6 | 비밀은 코드 밖 | 시크릿은 환경변수. 저장소·로그·캡처·브라우저로 나가는 값에 넣지 않는다 |
| 7 | 실패는 닫힌다 | 인증·권한 검사가 오류를 내면 허용이 아니라 거부 |
| 8 | 보안도 검증한다 | 통제마다 "뚫어 보는" 시험 시나리오를 둔다 (§15). 시험하지 않은 통제는 미검증 |

## 2. 인증과 세션 (관리자)

관리자만 로그인한다. 방문자 계정은 없다 (Phase 1).

| 항목 | 지침 |
| --- | --- |
| 비밀번호 저장 | 느린 해시를 쓴다 (argon2id 권장, scrypt 허용). 솔트 필수. **직접 구현하지 않고 검증된 라이브러리**를 쓴다. 평문·가역 암호화 저장 금지 |
| 비밀번호 규칙 | 최소 12자. 흔한 비밀번호 거부. 길이 상한(예: 1,024바이트)으로 해시 비용 공격 방지 |
| 2차 인증 | **관리자 계정은 2차 인증 적용을 기본으로 한다** (TOTP 등). 구현 방식은 열린 결정 (§16) |
| 로그인 시도 제한 | **IP와 계정 기준**으로 제한하고 일정 시간 잠금. (NexusPM의 단일 버킷 방식은 로컬 전용이라 그대로 쓰지 않는다.) 프록시 뒤에서는 신뢰할 수 있는 클라이언트 IP 출처를 정해 두고, 사용자가 조작할 수 있는 헤더를 그대로 믿지 않는다 |
| 오류 메시지 | "아이디 또는 비밀번호가 올바르지 않습니다"처럼 어느 쪽이 틀렸는지 알려 주지 않는다. 존재하지 않는 계정도 같은 시간이 걸리게 한다 (타이밍 차이 방지) |
| 세션 | 서버가 발급·검증. 쿠키 속성: `HttpOnly`, `Secure`, `SameSite=Lax` 이상. 예측 불가능한 값. 어드민 세션은 **최대 8시간** 만료 |
| 로그아웃 | 서버에서 세션을 폐기한다 (쿠키 삭제만으로 끝내지 않는다). 폐기된 세션 재사용 거부를 시험한다 |
| 로그인 후 | 세션 식별자를 새로 발급한다 (세션 고정 방지) |
| 비밀번호 재설정 | 이메일 링크 방식이면 1회용·단기 만료 토큰. 이메일 존재 여부를 노출하지 않는다. 계정 1~2개 규모이므로 **운영자가 직접 재설정하는 절차**로 대신할 수 있다 (열린 결정) |
| 초기 계정 | 비밀번호를 코드·문서에 두지 않는다. 최초 설정 절차를 환경변수 또는 1회용 링크로 한다 |
| 인증 우회 설정 | 개발 환경에서 인증을 끄는 설정은 **운영 빌드에서 무시**된다. 시험한다 (NexusPM의 방식 참고) |

## 3. 권한

| 역할 | 범위 | 비고 |
| --- | --- | --- |
| 관리자 (admin) | 모든 콘텐츠 관리, 신청 열람·처리, 사이트 설정 | Phase 1은 이 역할만 |
| (후보) 편집자 | 스토리·장비·후기 편집, 신청 열람 불가 | 공동 작업자 계정이 필요해질 때 |

- 권한 검사는 **어드민 화면 진입, 모든 데이터 변경, 모든 데이터 조회**에서 서버가 한다. 라우트 보호(미들웨어)만 믿지 않고, 데이터 접근 함수에서도 다시 확인한다 (한 겹이 뚫려도 다음 겹이 막는다).
- 신청 데이터와 사이트 설정은 관리자 전용으로 시작한다. 역할을 늘릴 때는 **가장 좁은 권한부터** 부여한다.

## 4. 접근 통제와 데이터 노출

- **공개 조회와 어드민 조회를 분리한다.** 공개용 함수는 공개 상태(`published`, 공개된 후기·장비, 종료되지 않은/아카이브된 투어)만 반환한다. 필터링은 **쿼리 단계**에서 한다 (가져온 뒤 화면에서 숨기지 않는다).
- **공개용 응답 모델(DTO)을 따로 둔다.** DB 행을 그대로 내보내지 않는다. 작성자 연락처, 내부 메모, 처리 상태, 수정자 같은 내부 필드가 공개 응답에 섞이면 결함이다.
- 임시저장 글과 비공개 항목의 URL을 직접 열면 **404**를 돌려준다 (존재 여부도 숨긴다). 미리보기는 관리자 세션이 있을 때만 가능하다.
- 임시저장·비공개 항목은 sitemap, RSS, 검색 색인, 소셜 미리보기에 나오지 않는다. 어드민 경로는 `noindex`이고 robots만으로 보호하지 않는다.
- 어드민의 식별자 기반 조회(`/admin/.../:id`)는 로그인 후에도 권한을 확인한다 (IDOR 방지). 목록 조회에 페이지 크기 상한을 둔다.
- 오류 응답에 스택·경로·SQL·내부 키를 노출하지 않는다.

## 5. 입력 검증과 출력 처리

| 대상 | 지침 |
| --- | --- |
| 모든 입력 | **서버에서 스키마로 검증**한다 (타입, 길이, 형식, 허용 값). 클라이언트 검증은 편의일 뿐 |
| SQL | 파라미터 바인딩 또는 ORM만 쓴다. 문자열 연결로 쿼리를 만들지 않는다 |
| 리치 텍스트 (스토리 본문) | **허용 목록 방식**으로 정제(sanitize)한다. 허용 태그·속성만 남기고 스크립트, 이벤트 속성, `javascript:` 링크를 제거한다. 저장할 때와 출력할 때 모두 신뢰하지 않는 값으로 다룬다 |
| 일반 텍스트 출력 | 기본이 이스케이프인 방식으로만 렌더링한다. 위험한 HTML 삽입 API는 정제를 거친 값에만 쓴다 |
| 링크·URL | 허용 스킴(`https`, `mailto`, `tel`)만. `javascript:`·`data:` 거부. 외부 링크는 `rel="noopener noreferrer"` |
| 영상 임베드 | **허용 도메인 목록**(예: YouTube, Vimeo)만. 임의의 iframe·스크립트 삽입 금지 |
| 리다이렉트 | 사용자 입력으로 목적지를 정하지 않는다 (열린 리다이렉트 방지). 로그인 후 이동 경로는 고정 |
| 경로·파일명 | 사용자 입력을 경로에 직접 쓰지 않는다 |
| 이메일 알림 | 사용자 입력이 헤더(수신자, 제목)에 들어가지 않게 하고, 본문은 이스케이프한다 (헤더 삽입 방지) |
| 슬러그 | 허용 문자만. 예약어(`admin`, `api`) 거부 |

## 6. 요청 출처와 CSRF

- 상태를 바꾸는 요청은 GET으로 하지 않는다.
- 쿠키 기반 세션이므로 **CSRF 방어**를 적용한다: `SameSite` 쿠키 + Origin/Referer 검사 또는 토큰. 사용하는 프레임워크의 기본 보호가 있다면 **무엇을 막고 무엇을 막지 않는지 문서로 확인**하고 시험한다. 가정하지 않는다.
- 다른 출처의 폼에서 어드민 변경 요청이 거부되는지 시험한다 (§15).
- 공개 폼 제출 엔드포인트의 CORS는 필요한 출처만 허용한다.

## 7. 파일 업로드 (이미지)

| 항목 | 지침 |
| --- | --- |
| 허용 형식 | **이미지 allowlist** (JPEG, PNG, WebP, AVIF). 확장자만 보지 않고 **파일 내용(매직 넘버)과 MIME을 서버에서 확인** |
| SVG | 사용자 업로드 SVG는 **받지 않는다** (스크립트를 담을 수 있음). 로고·일러스트는 개발자가 코드로 관리 |
| 크기 | 파일 크기, 이미지 해상도, 요청 전체 크기에 상한 |
| 파일명 | 원본 이름을 쓰지 않고 **서버가 무작위 이름을 새로 만든다.** 경로 문자 제거 |
| 메타데이터 | 사진의 **위치정보(EXIF GPS) 등 메타데이터를 제거**하거나 최소화한다 (투어 사진 프라이버시) |
| 저장 | 웹 서버 실행 영역 밖의 객체 스토리지. 업로드 경로에서 코드가 실행되지 않게 한다 |
| 접근 | 공개 이미지는 공개 URL, 비공개 이미지는 서명된 임시 URL 또는 서버 경유. 업로드 권한은 관리자만 |
| 처리 | 리사이즈·변환은 신뢰된 라이브러리로. 이미지 파서의 취약점 소식을 의존성 점검에 포함 |
| 정리 | 사용하지 않는 파일(고아 파일)을 주기적으로 정리하는 절차 |

## 8. 공개 폼 보호 (투어 신청·문의)

공개 폼은 자동화된 남용의 첫 표적이다.

| 통제 | 지침 |
| --- | --- |
| 서버 검증 | 필수값, 길이 상한, 형식(이메일·전화), 허용 값, 인원 범위 |
| 스팸 방지 | **허니팟 필드 + 제출 빈도 제한(IP·시간 기준)**을 기본으로 한다. 부족하면 캡차를 도입한다. 외부 캡차 서비스는 개인정보·비용·접근성 영향을 검토한 뒤 결정 (§16) |
| 중복 제출 | 같은 내용의 연속 제출 방지 (제출 중 버튼 잠금 + 서버 측 멱등 처리) |
| 동의 | 개인정보 수집·이용 동의 체크 필수. **동의 일시와 동의 문구 버전을 저장** |
| 응답 | 성공·실패 메시지에 내부 정보를 담지 않는다. 처리 상태를 신청자에게 노출하지 않는다 |
| 알림 | 알림 메일 발송이 실패해도 신청 데이터는 저장하고, 실패를 어드민에 표시한다. 메일 서비스의 남용 한도를 설정한다 |
| 접수 확인 메일 | 도입 시 신청자가 입력한 주소로만 보내고, 무제한 재발송을 막는다 (타인에게 스팸을 보내는 도구가 되지 않게) |
| 소식 받기 폼 | 이름·이메일·동의만 받는 최소 폼에도 같은 검증·허니팟·속도 제한을 적용한다. 안내는 규강이 개별로 연락한다. **일괄 메일을 보내면 광고성 정보 전송에 해당할 수 있어** 별도 동의, 수신 거부 방법, 발송 기준을 법률 확인 후 정한다 |

## 9. 개인정보

| 항목 | 지침 |
| --- | --- |
| 최소 수집 | 이름, 연락처, 이메일, 문의 내용, 인원, 경험·자격 정도. 주민번호 등 불필요한 정보는 받지 않는다. 폼 항목 추가는 필요성을 검토한 뒤 |
| 처리방침 | **개인정보 처리방침 페이지**를 공개 전에 마련한다 (수집 항목, 목적, 보유 기간, 파기, 처리 위탁, 열람·삭제 요청 방법). 법률 요건은 전문가 확인 |
| 보유 기간 | 처리 완료 후 일정 기간만 보관하고 파기한다. 기간은 열린 결정 (§16). 파기 절차(어드민에서 삭제 + 백업에서의 소멸 시점)를 정한다 |
| 접근 | 신청 데이터는 관리자만 열람. 열람과 내보내기를 로그로 남긴다 |
| 처리 위탁·제3자 | 호스팅, DB, 메일 발송, 분석 도구 등 개인정보가 거치는 서비스를 목록으로 관리하고 처리방침에 반영한다. 해외 서비스는 국외 이전 고지 여부를 확인한다 |
| 쿠키·분석 | 분석 도구나 광고 스크립트를 쓰면 고지와 동의 방식을 정한다. 필수 쿠키(관리자 세션)만 쓰는 공개 사이트는 배너가 필요 없을 수 있으나 확인한다. 외부 글꼴 CDN도 접속 정보가 전달되므로 자체 호스팅을 권장 ([CONCEPT §7.8](CONCEPT.md)) |
| 후기 | 작성자의 공개 동의와 표기 방식(실명, 이니셜, 닉네임)을 기록한다. 철회 요청 절차를 둔다 |
| 로그·캡처 | 개인정보를 남기지 않는다 ([DEVELOPMENT §5](DEVELOPMENT.md)). 테스트에는 가상 데이터만 쓴다 |
| 백업 | 백업에도 개인정보가 있다. 암호화된 저장, 접근 제한, 보관 기간을 정한다 |
| 유출 사고 | 대응 절차를 §14에 정해 둔다. 신고·통지 의무는 전문가 확인 |

## 10. 시크릿과 환경

- 모든 시크릿은 **환경변수**(호스팅의 비밀 저장소)로 주입한다. 코드, 문서, 이슈, PR에 넣지 않는다. `.env`는 git 무시, `.env.example`에는 **키 이름만** 둔다.
- **환경별로 분리한다**: 로컬 / 프리뷰 / 운영의 DB, 스토리지, 메일 키를 서로 다르게 쓴다. 프리뷰에서 운영 DB에 접속하지 않는다.
- **브라우저로 나가는 값에 비밀을 넣지 않는다.** 프레임워크에서 클라이언트 번들에 노출되는 환경변수 규칙(접두어 등)을 확인하고, 공개용 값만 그 방식으로 노출한다. 서버 전용 모듈이 클라이언트에 들어가지 않는지 빌드 결과를 확인한다.
- 서드파티 키는 **최소 권한**으로 발급하고 용도별로 나눈다 (읽기 전용 키 등).
- 로그, 캡처, Playwright 추적, 오류 보고에서 시크릿을 마스킹한다. 환경변수 전체를 출력하지 않는다.
- 시크릿이 유출됐다면 **키 교체가 첫 조치**이고, 이력 정리는 그다음이다. 교체 절차를 미리 적어 둔다.
- 시크릿 스캔(커밋 전·CI)을 도입한다. 공개 저장소 전환 시 이력 전체를 먼저 점검한다.

## 11. 의존성과 공급망

- 새 패키지는 설치 전에 **라이선스(상업 이용 가능), 유지보수 상태, 다운로드 규모, 설치 스크립트 유무**를 확인한다. 이름이 비슷한 가짜 패키지에 주의한다.
- lockfile을 커밋하고, 설치는 lockfile 기준으로 한다. 업데이트는 **한 번에 하나**씩 (롤백 용이).
- 취약점 알림(Dependabot 등)과 `audit` 점검을 정기 절차로 둔다. 운영 의존성과 개발 의존성을 구분하고, 개발용 생성기를 운영에 포함하지 않는다.
- 보안 패치는 지체 없이, 새 메이저는 안정화 후 ([DEVELOPMENT §10](DEVELOPMENT.md)). 긴급 갱신도 검증 게이트를 생략하지 않는다.
- 외부 스크립트(분석, 위젯, 임베드)는 최소화한다. 불가피하면 출처를 CSP에 명시하고 정기적으로 점검한다.
- AI가 제안한 패키지는 **실제로 존재하고 신뢰할 만한지 확인**한다 (없는 패키지를 제안하는 환각이 있을 수 있다).
- 학습용 키트·타인의 코드를 복사하지 않는다. 사용 조건을 확인한다 ([PRD §10](PRD.md)).

## 12. 전송과 보안 헤더

| 항목 | 지침 |
| --- | --- |
| HTTPS | 전체 HTTPS. HTTP는 HTTPS로 리다이렉트. HSTS 적용 (도메인이 확정된 뒤 기간을 늘린다) |
| CSP | 허용 출처 목록 방식. 이미지·글꼴·영상 임베드(YouTube/Vimeo)·분석 출처만 허용. 인라인 스크립트는 nonce 또는 해시. 처음에는 report-only로 시험한 뒤 적용 |
| 기타 헤더 | `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `frame-ancestors`(클릭재킹 방지), `Permissions-Policy`로 불필요한 기능 차단 |
| 쿠키 | `Secure`, `HttpOnly`, `SameSite` |
| 캐시 | 어드민과 개인정보가 담긴 응답은 `no-store` |
| 오류 페이지 | 기술 정보를 노출하지 않는 404·500 |
| 도메인 변경 | 도메인이 바뀌어도 쿠키·CSP·CORS·메일 링크가 `SITE_URL`을 따르는지 확인 ([PRD §12.4](PRD.md)) |

## 13. 인프라, 계정, 개발 과정

호스팅이 열린 결정이므로 **호스팅과 무관한 공통 통제**를 먼저 적는다. 호스팅이 정해지면 구체화한다.

| 영역 | 지침 |
| --- | --- |
| 계정 보호 | GitHub, 호스팅, 도메인 등록처, DNS, 메일·스토리지 서비스의 계정에 **2차 인증**을 켠다. 복구 수단을 안전하게 보관 |
| 도메인 | 등록처 잠금(전송 잠금), 자동 갱신, 소유자 이메일 접근 확보. 도메인 탈취는 사이트 전체의 탈취다 |
| 이메일 인증 | 사이트 도메인에서 메일을 보낸다면 SPF, DKIM, DMARC 설정 |
| 데이터베이스 | 인터넷에서 직접 접속되지 않게 한다. 애플리케이션용 계정은 **최소 권한**. 자동 백업과 **복원 시험** |
| 스토리지 | 기본 비공개. 공개가 필요한 객체만 공개 |
| 프리뷰·스테이징 | 접근 보호를 걸고, 운영 데이터와 분리, 가상 데이터만. 인증 없는 미리보기를 운영 배포로 안내하지 않는다 |
| 비용 남용 | 사용량 한도와 알림을 설정한다 (서버리스형은 남용 요청이 비용으로 이어진다) |
| 속도 제한 | 로그인과 폼 엔드포인트에 호스팅·엣지 수준의 제한을 더하는 방안 검토 |
| GitHub 저장소 | `main` 브랜치 보호(직접 푸시 금지, PR 필수), 협업자 권한 최소화, 시크릿 스캔 켜기. 저장소가 공개로 바뀔 때의 점검 목록 마련 |
| AI 작업 환경 | AI 세션에는 필요한 권한만 준다. 파괴적 명령(삭제, 강제 푸시, 운영 변경)은 사용자 확인 후 실행. 시크릿을 채팅에 붙여 넣지 않는다 |
| 개발 PC | 디스크 암호화, 화면 잠금, OS 업데이트 |

## 14. 로깅, 모니터링, 사고 대응

### 14.1 보안 이벤트 로그

[DEVELOPMENT §5](DEVELOPMENT.md)의 구조화 로그에 다음을 포함한다: 로그인 성공·실패·잠금, 권한 거부, 세션 폐기, 업로드 거부(사유), 폼 스팸 차단, 입력 검증 거부 급증, 신청 데이터 열람·내보내기·삭제, 관리자 설정 변경. **개인정보와 비밀은 기록하지 않는다.**

### 14.2 알림

로그인 실패 급증, 오류율 급증, 비정상 트래픽, 비용 한도 도달, 메일 발송 실패는 규강에게 알림이 가게 한다 (방법은 호스팅 결정 후).

### 14.3 사고 대응 5단계

1. **탐지·확인**: 무엇이, 언제부터, 어디까지 영향을 받았는지 사실만 기록
2. **격리**: 의심 계정 정지, 세션 전체 폐기, 필요하면 어드민 일시 차단
3. **시크릿 교체**: 노출 가능성이 있는 모든 키와 비밀번호를 교체 (§10)
4. **복구**: 백업에서 복원하고 정상 동작을 확인
5. **기록·재발 방지**: 원인, 영향 범위, 조치를 기록하고 통제를 보강. 개인정보 유출이 의심되면 신고·통지 의무를 전문가와 확인

## 17. 마켓(상품 판매)으로 확장할 때 추가되는 것

Phase 1 범위는 아니지만 설계 때 막지 않도록 미리 적는다.

- **결제 정보는 직접 받거나 저장하지 않는다.** 검증된 결제 대행(PG)의 호스팅 결제 화면·토큰을 쓴다.
- 주문 금액과 재고는 **서버에서 계산하고 검증**한다 (클라이언트가 보낸 가격을 믿지 않는다).
- 전자상거래 관련 고지(사업자 정보, 환불·교환 정책, 청약철회 등)와 약관이 필요하다. 법률 확인.
- 주문·고객 정보는 신청 데이터보다 높은 수준으로 보호하고, 결제 웹훅은 서명을 검증한다.
- 회원 로그인이 생기면 이 문서의 §2~§4를 방문자 계정 기준으로 확장한다.
